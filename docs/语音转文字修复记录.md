# 语音转文字（ASR）问题修复记录

> 记录时间：2026-09-21
> 涉及文件：`src/main/input/transcription.ts`（主进程转写链路）、`src/renderer/src/lib/audio-capture.ts`（渲染进程音频采集）

## 背景与问题表现

应用原有的语音转文字链路为：全局快捷键触发 → 渲染进程采集音频（麦克风或系统音频 loopback）→ 主进程经 WebSocket 对接阿里云百炼 `fun-asr-realtime` 实时识别 → 文本随截图自动提交给后台 AI。

实际使用中暴露出三类问题：

| # | 表现 | 严重程度 |
|---|------|----------|
| 1 | 切换到 `qwen3-asr-flash-realtime` 后直接报错 `Model not found (close code 1007)`，完全不可用 | 阻断 |
| 2 | 语速较快时出现**叠字**（同一段话被重复识别/重复显示）；系统音频模式下偶发声音重影 | 高 |
| 3 | 点击停止转录/快捷键结束会话时，**最后一句话经常丢失** | 中 |

---

## 问题 1：协议端点接错（`Model not found`）

### 根因

`qwen3-asr-flash-realtime` 属于 **Qwen-ASR-Realtime** 系列，走的是全新的 **OpenAI Realtime 风格协议**（URL 带 `?model=` 参数，用 `session.update` / `input_audio_buffer.append` / `session.finish` 事件），而不是老的 `run-task` duplex 端点 `/api-ws/v1/inference`。老端点不认识这个模型名，服务端以 close code 1007 关闭连接并返回 `Model not found。旧模型 `fun-asr-realtime` 恰好兼容老端点，所以此前能正常连上，掩盖了端点与模型的绑定关系。

### 问题代码（原 `transcription.ts`）

```ts
const WS_URL = 'wss://dashscope.aliyuncs.com/api-ws/v1/inference/'

ws.on('open', () => {
  const runTask = {
    header: {
      action: 'run-task',        // 旧 duplex 协议专有指令
      task_id: taskId,
      streaming: 'duplex'
    },
    payload: {
      task_group: 'audio',
      task: 'asr',
      function: 'recognition',
      model: 'qwen3-asr-flash-realtime',  // 新模型被喂给了旧端点
      parameters: { format: 'pcm', sample_rate: 16000 },
      input: {}
    }
  }
  ws!.send(JSON.stringify(runTask))
})
```

### 修复

整条链路改写为新 Realtime 协议（见 [官方客户端事件文档](https://help.aliyun.com/zh/model-studio/qwen-asr-realtime-client-events)、[服务端事件文档](https://help.aliyun.com/zh/model-studio/qwen-asr-realtime-server-events)）：

```ts
// 连接新端点，模型名放在 query 上
const WS_URL =
  'wss://dashscope.aliyuncs.com/api-ws/v1/realtime?model=qwen3-asr-flash-realtime'

// 连接建立后第一步：会话配置（官方推荐值：VAD 阈值 0.0、断句 400ms）
const sessionUpdate = {
  event_id: nextEventId(),
  type: 'session.update',
  session: {
    input_audio_format: 'pcm',
    sample_rate: 16000,
    input_audio_transcription: { language: 'zh' },
    turn_detection: {
      type: 'server_vad',
      threshold: 0.0,
      silence_duration_ms: 400
    }
  }
}

// 音频改为逐块 base64 追加进服务端缓冲区（VAD 模式自动提交识别）
{
  event_id: nextEventId(),
  type: 'input_audio_buffer.append',
  audio: Buffer.from(chunk).toString('base64')
}
```

## 问题 2：叠字 / 重影（两层原因）

### 2a. 主进程拼接层：心跳包与重复的最终结果被重复累加

**表现**：语速快时同一段文字出现两遍。

**官方协议本意**（旧协议）：

- 携带 `heartbeat: true` 的 `result-generated` 是心跳包（`sentence_id=0`），文本无意义，**应跳过**；
- `sentence_end=true` 的最终结果**理论上每句只发一次**，但语速快时服务端可能对同一 `sentence_id` 重发最终结果。
- 原代码对两者都没有防护，无条件 `accumulatedText += text`，同一句就被追加两次。

**问题代码**：

```ts
ws.on('message', (data) => {
  // ...
  if (event === 'result-generated') {
    const sentence = msg.payload?.output?.sentence
    const text = sentence.text || ''
    const sentenceEnd = sentence.sentence_end === true

    if (sentenceEnd) {
      if (text) {
        accumulatedText += text        // ← 没有 sentence_id 校验，重发必叠字
      }
      currentPartial = ''
    } else {
      currentPartial = text            // ← 没有跳过 heartbeat 包
    }
  }
})
```

**修复**：

```ts
// 心跳包（sentence_id 0）直接跳过，避免与上一句的句尾内容重叠
if (sentence.heartbeat === true) return

if (sentenceEnd) {
  // 只有从未定稿过的句子才允许累加，重发的最终结果不可能重复追加
  if (text && sentenceId > lastFinalSentenceId) {
    accumulatedText += text
    lastFinalSentenceId = sentenceId
  }
  currentPartial = ''
}
```

新协议下等价改为了按 `item_id` 跟踪：部分结果是 `text`（已确认前缀）+ `stash`（可变草稿），最终结果 `conversation.item.input_audio_transcription.completed` 的 `transcript` 按 item 去重后累加，从协议层面杜绝重复。

### 2b. 音频采集层：抓到的系统音频被重放回扬声器形成回声重影

**表现**：系统音频模式下，识别文本出现"鬼影"、音量加倍、偶发回声。

**根因**：`startAudioCapture()` 里，处理节点**直连**了 AudioContext 的 destination：

```ts
const processor = audioContext.createScriptProcessor(2048, 1, 1)
processor.onaudioprocess = (e) => downsampleAndSend(e.inputBuffer.getChannelData(0))
source.connect(processor)
processor.setSinkId?.(audioOutputDeviceId) // 仅外放 token 有效
processor.connect(audioContext.destination) // ← 抓到的声音被原样再外放
```

ScriptProcessor 必须连着 destination 才会被调度，但这导致 loopback 抓到的系统音频**从 default-扬声器再次播放**——而那正是被采集的设备，回放声又被卷进下一次采集 → 音频绕环 → ASR 收到重复样本（叠字的物理来源）。麦克风模式下同一机制等价于"自己听到自己的回声"。此外 `new AudioContext({ sampleRate: 16000 })` 强制把 48k/44.1k 的 loopback 流隐式重采样到 16k，Chromium 对虚拟 loopback 源 + 目标速率不匹配存在丢块/重复块的历史问题。

**修复**（`audio-capture.ts`）：

1. 经**增益为 0 的中间节点**路由：ScriptProcessor 保持被调度、正常拉流，但不再外放；
2. AudioContext 改用**设备原生采样率**，在 JS 里手动线性插值下采样到 16k，行为完全确定：
3. 顺带移除了「监听输出」（`setSinkId`）路径——它正是重影的直接来源。

```ts
source.connect(processor)
// 静音后路由到 destination：保住 ScriptProcessor 的拉流调度，但不外放
const mute = audioContext.createGain()
mute.gain.value = 0
processor.connect(mute)
mute.connect(audioContext.destination)
```

```ts
// JS 手动线性插值下采样，替代 new AudioContext({ sampleRate: 16000 }) 的隐式重采样
function resampleTo16k(input: Float32Array, inputRate: number): Float32Array {
  if (inputRate === TARGET_SAMPLE_RATE) return input
  const ratio = inputRate / TARGET_SAMPLE_RATE
  const outputLength = Math.floor(input.length / ratio)
  const output = new Float32Array(outputLength)
  for (let i = 0; i < outputLength; i++) {
    const pos = i * ratio
    const idx = Math.floor(pos)
    const frac = pos - idx
    output[i] = input[idx] + (input[Math.min(idx + 1, input.length - 1)] - input[idx]) * frac
  }
  return output
}
```

## 问题 3：停止转录时丢最后一句话

**表现**：点击停止（或快捷键结束会话）后核对文本，最后一句话不见了。

**根因**：原代码发送结束指令后**立即** `cleanup()` 断开连接，服务端最后一段音频的收尾结果（含标点和句尾更正）还没来得及返回就被掐断了。

**问题代码**：

```ts
function stopTranscription() {
  if (!isTranscribing) return
  if (ws && ws.readyState === WebSocket.OPEN && taskStarted) {
    ws.send(JSON.stringify(finishTask))
  }
  isTranscribing = false
  cleanup()                    // ← 立刻断连，尾句结果丢失
  sendToRenderer('transcription-stopped')
}
```

**修复**：保留连接，等服务端确认会话结束再清理：

```ts
ws.send(JSON.stringify({ event_id: nextEventId(), type: 'session.finish' }))
// 等服务端发回 session.finished（旧协议为 task-finished）后 cleanup；
// 服务端文档明确：客户端收到该事件后才可主动断连。
// 附 3 秒兜底超时防服务端失联：
finishTimeout = setTimeout(() => {
  cleanup()
  sendToRenderer('transcription-stopped')
}, 3000)
```

## 附带升级与遗留提醒

- **模型升级**：`fun-asr-realtime` → `qwen3-asr-flash-realtime`（千问 3 ASR 实时版）。与 Fun-ASR 同一把百炼 Key、同一账户体系，按量计费（约 0.8–1.2 元/小时），无需额外开通服务。
- **遗留提醒 1**：Windows 上 Chrome 的 loopback 只能抓**默认播放设备**的声音。若会议/播放软件的音频输出在蓝牙耳机、HDMI 等非默认设备上，系统音频模式会抓到空白。
- **遗留提醒 2**：设置页的「音频输出设备（监听输出）」已不再参与采集——原"监听"行为正是问题 2b 的直接来源，该下拉框可忽略。
- **验证方式**：`npm run dev` 后开启转录，播放一段语速较快的中文视频（系统音频模式）或正常语速对着麦克风说话（麦克风模式），观察：无叠字、标点正常、停止后不丢尾句。
